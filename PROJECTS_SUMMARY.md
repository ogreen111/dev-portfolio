Reviewing the *plan* caught nine real implementation bugs before a line of it was written: OAuth scope hardcoded to commercial Graph (breaking GCC-High/DoD), unescaped path segments in Graph URLs (breaking on filenames containing `#` or `?`), `if_match` silently dropped on chunked uploads, two `push_retry` tests that could never have passed as drafted, `push()` accepting a `local_path` outside `cache_dir` while retry-recovery assumed otherwise and would silently abandon such uploads forever, `pending_delete` defined in the data model and claimed by `sync()`'s own docstring but never implemented, delta tombstones commonly lacking `parentReference` and so breaking the ancestry-based scope filter for deletions, a loop bug in the ancestry walk that silently ignored items nested more than one level below a known-but-not-in-batch ancestor, and `download_content()` being called on folder items that have no `/content` endpoint. A further push-time review closed genuine data-loss and staleness gaps in the built module: `push_retry()` now raises `RemoteConflict` on a content-hash mismatch instead of blindly overwriting what may be an unrelated concurrent write; `delete()` no longer crashes on a folder entry (an empty `local_filename` resolved to `cache_dir` itself, and unlinking a directory raised `IsADirectoryError` *after* the remote delete had already succeeded, permanently stranding the entry); a first bootstrap sync with no persisted delta token is treated as a full resync for pruning purposes, exempting items that same `sync()` call just confirmed so a push Graph hasn't caught up to isn't immediately deleted again; a deleted folder's tombstone cascades recursively to every tracked descendant, since Graph emits one tombstone per deleted folder rather than one per contained item; and simple upload, each chunk of a chunked upload, and `move_item` all go through the shared retry wrapper instead of failing outright on an ordinary 429/502/503/504. Two details worth carrying forward: `push_retry()` recognizes a matching prior upload by **quickXorHash** — ported from Microsoft's reference implementation and verified against the documented test vector — because SharePoint and OneDrive-for-Business drives, this migration's actual target, only ever return that and never `sha256Hash`; and a delta-token crash-ordering test that only checked happy-path final state (token and file both present, which can't distinguish "persisted last" from "persisted first") was joined by one that forces a mid-batch failure and asserts the token did *not* advance. **2026-08-15 was a correctness pass over that same module — still with zero live wiring** — and its headline fix would have broken the first real run: `get_item_by_path()` built `/items/root:/{path}` for the drive-root bootstrap case, but Graph's actual syntax is `/root:/{path}` (`root` is valid only as that literal path segment, never as an item id under `/items/`), so first-time root bootstrap would have 404'd against the live API. It was found by checking Microsoft's own documentation, not by a test — though not because mocks are structurally incapable here: the regression test added with the fix is itself fully mocked and asserts the request URL against Graph's documented syntax. The reason the suite missed it is narrower and more ordinary — the existing mocks were written from the same mistaken assumption as the code, so they agreed with it. Three more landed with it: `push()` now rejects an absolute `relative_path` or one containing `..`, because `cache_dir / "/etc/passwd"` evaluates to `/etc/passwd` (an absolute right-hand side wins in path division rather than erroring, so the existing equality check couldn't catch it) and a stored escaping filename would later reach `unlink()`; the moved-outside-root cleanup in `sync()` now cascades to tracked descendants via the same recursive helper a real deletion uses, since Graph's delta doesn't reliably re-emit a folder's children just because the folder moved; and `resolve()`/`sync()` no longer hold `root_lock` across the Graph network calls, which contradicted `graph/lock.py`'s own documented contract. Releasing that lock exposed two races, both closed directly: a deterministic tmp filename let two concurrent downloads of the same item collide (now a per-call-unique `_stage_content()`), and a slower download could clobber a faster concurrent write's newer result (now discarded atomically after re-checking the entry's etag against a pre-download snapshot). A further set of concurrency findings was evaluated and deliberately left open, which is the more interesting judgment: overlapping `sync()` calls can persist delta tokens out of order (opaque tokens, no client-side ordering available), an in-flight download can resurrect an item a concurrent `delete()` removed, full-resync pruning can delete an entry a concurrent `resolve()`/`push()` added after its snapshot, and path confinement doesn't account for a symlink planted inside `cache_dir` (which needs an already-compromised cache to matter). None corrupts file *content*, and the deployment is single-writer-per-root regardless, but the "a later sync self-heals" half of that reasoning does not hold uniformly: in the resurrect-on-delete case, `resolve()`'s post-download guard only discards its result when the entry still exists with a changed etag, so an entry a concurrent `sync()` deleted mid-download is written straight back — and since that tombstone has already been consumed and the delta token advanced past it, no *incremental* sync will ever re-emit it. That one needs a full resync to prune; the other three do self-heal on a later sync or resolve. Closing them properly requires a second, coarser whole-`sync()` lock, tracked as a real design addition rather than improvised. **2026-08-18 shipped Plan 2 of 3 in sixteen commits and closed the credential question that gated the migration**: Owen chose to reuse rfp-automation/SENTRY's existing certificate and app registration rather than provision a separate one — no code impact here (auth is Plan 1 code), but it clears Plan 3 to go to live credentials. Plan 2 is the **nested-cache retrofit**, and the reason it had to exist is concrete: Plan 1's cache stored every file flat under `cache_dir` with an id-derived stem, which cannot satisfy the locked spec's promise that "everything downstream keeps doing ordinary `Path` I/O unchanged" — `dashboard.py` scans `vault_root.iterdir()` and `sub.glob("*.docx")`, and the webserver mounts `StaticFiles(vault_root)`. So `CacheEntry.local_filename` now means a root-relative POSIX path rather than a bare filename, derived by walking `parent_id` ancestry with **on-demand ancestor healing** (unknown parent folders are fetched from Graph and registered) so path derivation never depends on delta batch ordering, and a per-root **naming policy** keeps real basenames for the app-authored deterministic names downstream globs actually look for (`summary.md`, `email.*`, `*.docx`) while giving everything externally named a collision-safe id-stem. The write-side primitives Plan 3 will call landed with it: `create_folder` (409-adopt), `ensure_remote_dir`, `push_update` (If-Match + crash-safe pending retry), a write-ahead `move`, and `push_tree`. The day's most consequential fix was a data-loss path the spec had described and the code had never implemented — the "Sync ordering" rule that a local pending write beats a same-cycle incoming delta. `_apply_delta_item` never checked pending state, so a same-batch tombstone for an item whose `push_update` had failed would unlink the local file and drop the entry, destroying never-uploaded edits, while the pending-update loop's own comment claimed the case was safely reconciled. ## siem-forwarder
**Purpose:** Niagara 4 JACE module forwarding security-relevant BACnet MS/TP operations — decoded from *all* traffic on a monitored RS-485 trunk by a receive-only passive listener — to a SIEM over RFC 5424 syslog/TLS, with a non-interference design: bounded drop-oldest queue, below-normal-priority worker, self-throttling with gap events. **Stack:** Java (Niagara 4 module API, Gradle).
**Notes:** Skeleton/design-complete; existing call sites written against the Niagara 4.15.1 API surface, bind points remaining for the target build (slot-o-matic, TLS trust store). Code is still untouched since the 2026-08-05 extraction, but **the design changed shape on 2026-08-11** and the SDD is now at **v1.8 (draft)**. PNNL's answer to a July design-clarification email — capture *all* RS-485 bus traffic, not only points already monitored elsewhere — is more than the ride-along point-COV pattern could deliver: ride-along only saw Niagara-abstracted values for points some other component already had subscribed, never the on-wire operations where the security signal actually lives (Who-Is/Who-Has recon sweeps, priority-array `WriteProperty` seizures and null-outs, `DeviceCommunicationControl`/`ReinitializeDevice`, a new MAC joining the token ring). So **v1.5 retired ride-along outright** rather than keeping it as a secondary collector (`RideAlongSubscriber` → `AlarmSubscriber`, `MstpPassiveListener` introduced as primary), and **v1.6 retired alarm forwarding as well** — scope is now exclusively field-bus traffic, with the listener doing its own ALARM-severity classification of wire events; the two safety patterns renumbered to #1 bounded queue and #2 self-throttle. The §13 listener is a dedicated receive-only serial port jumpered onto the live trunk (Port 1 masters BACnet normally, Port 2 listens), running a custom MS/TP frame state machine and BACnet APDU decoder that is explicitly *not* layered on Tridium's driver.
