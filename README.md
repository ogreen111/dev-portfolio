#### rfp-automation
Automated extraction, analysis, and proposal generation for DoD/MILCON cybersecurity RFPs. Parses specs and drawings, classifies cyber governance (UFGS 25 05 11 / 25 08 11), extracts scope, builds submittal matrices, and generates draft proposals. 2026 additions: email intake with PIID identity gate, bid follow-up tracking with Planner comment integration, amendment cyber review (local Ollama for CUI, cloud otherwise), redesigned dashboard with SSE live updates, per-project Ask-AI chat, a launchd-driven SENTRY self-improvement loop, and (August) a **missing-RFP-docs flag** — a pipeline-independent watch-loop sweep that surfaces MISC-type project folders whose `0.RFP/` holds no source documents, which `parser.discover_projects` had been filtering out silently. Surfaces in the dashboard attention inbox and the daily digest, behind `RFP_MISSING_DOCS_ENABLED`. Review caught nine real bugs in the drafted code *before it was written* (OAuth scope hardcoded to commercial Graph, unescaped Graph URL path segments, `if_match` silently dropped on chunked uploads, `pending_delete` documented but never implemented, tombstones commonly lacking `parentReference`, a loop bug in the ancestry walk, and more), and a push-time review round then closed real data-loss gaps in the built code: `push_retry()` raises `RemoteConflict` on a content-hash mismatch instead of overwriting what might be an unrelated concurrent write, `delete()` no longer strands a folder entry by trying to unlink a directory after the remote delete already succeeded, bootstrap syncs are treated as full resyncs for pruning while exempting items the same call just confirmed, folder tombstones cascade to every tracked descendant, and the chunked/simple upload and move paths all go through the retry wrapper. Notably, `push_retry()` matches a prior upload by **quickXorHash** (ported from Microsoft's reference implementation and checked against the documented test vector), because SharePoint and OneDrive-for-Business drives — this migration's actual target — never return `sha256Hash`. The 08-13 dedup work also got one more review pass: an unforced JSON key rename was reverted, and a folder-name-reuse regression test that had quietly stopped proving anything was renamed and re-documented to say exactly what it does and doesn't cover, with the parallel `VaultIndex`-side name-staleness problem filed as pre-existing follow-up rather than folded in. **2026-08-15 was a correctness pass over that merged `graph/` module — still with zero live wiring** — and its headline fix would have broken the very first real run: `get_item_by_path()` built `/items/root:/{path}` for the drive-root bootstrap case, but Graph's actual syntax is `/root:/{path}` (`root` is only valid as that literal path segment, never as an item id under `/items/`), so first-time root bootstrap would have 404'd against the real API. It was caught by checking Microsoft's own documentation rather than by a test — not because a mocked suite is incapable of catching it (the regression test added with the fix is itself fully mocked, asserting the request URL against the documented syntax), but because the existing mocks had encoded the same wrong assumption as the code they were exercising. Three more landed with it: `push()` now rejects an absolute `relative_path` or one containing `..`, because `cache_dir / "/etc/passwd"` evaluates to `/etc/passwd` — an absolute right-hand side wins in path division rather than erroring, so the existing equality check couldn't catch it, and a stored escaping filename would later be handed to `unlink()` during delete/cleanup/crash-recovery; the moved-outside-root cleanup in `sync()` now cascades to tracked descendants through the same recursive helper a real deletion uses, since Graph's delta doesn't reliably re-emit a folder's children just because the folder moved; and `resolve()`/`sync()` no longer hold `root_lock` across the Graph network calls, which contradicted `graph/lock.py`'s own documented contract — releasing it exposed two races that were then closed directly, a deterministic tmp filename letting two concurrent downloads of the same item collide (now a per-call-unique `_stage_content()`) and a slower download clobbering a faster concurrent write's newer result (now discarded atomically after re-checking the entry's etag against a pre-download snapshot). A further set of concurrency findings was evaluated and *deliberately* left open, which is the more interesting call: overlapping `sync()` calls can persist delta tokens out of order (the tokens are opaque, so there's no client-side ordering to impose), an in-flight download can resurrect an item a concurrent `delete()` removed, full-resync pruning can delete an entry a concurrent `resolve()`/`push()` added after its snapshot, and path confinement doesn't account for a symlink planted inside `cache_dir` (which needs an already-compromised cache to matter). None corrupts file *content*, and the deployment is single-writer-per-root anyway, but the self-healing claim needs one carve-out: the resurrect-on-delete race leaves a stale index entry that an *incremental* sync will not clear, because the tombstone that would remove it was already consumed and the delta token advanced past it — only a full resync prunes it. The others do self-heal on a later sync or resolve. Closing them properly needs a second, coarser whole-`sync()` lock, which is a real design addition tracked as follow-up rather than improvised here. **2026-08-18 delivered Plan 2 of 3 in a single day — sixteen commits — and resolved the credential question that had been gating the whole migration.** Owen chose **(a) reuse rfp-automation/SENTRY's existing certificate and app registration** rather than provisioning a separate one; that has no code impact on this plan (auth is Plan 1 code) but unblocks Plan 3 to proceed to live credentials. Plan 2 itself is the **nested-cache retrofit**, and its necessity is worth stating plainly: Plan 1's `Cache` stored every file flat under `cache_dir` with an id-derived stem, which is structurally incompatible with how the app already reads the vault — `dashboard.py` does `vault_root.iterdir()` and `sub.glob("*.docx")`, and the webserver mounts `StaticFiles(vault_root)`. The locked spec's promise that "everything downstream keeps doing ordinary `Path` I/O unchanged" simply could not hold on a flat store, which is why this was recorded as the known blocker on 08-17. So `CacheEntry.local_filename` changed meaning from a bare filename to a root-relative POSIX path, with paths derived by walking `parent_id` ancestry through the index and **healing unknown ancestors on demand** (fetching and registering parent folders from Graph), so derivation never depends on the order Graph happens to emit a delta batch. A per-root **naming policy** decides which files keep their real basename — the app-authored deterministic ones (`summary.md`, `email.*`, `*.docx`) that downstream globs actually look for — versus which get the collision-safe id-stem (everything externally named, where a hostile or colliding filename is a real risk). The same plan added the write-side primitives Plan 3 will call: `create_folder` (with 409-adopt), `ensure_remote_dir` to walk and create remote folder chains, `push_update` with `If-Match` and crash-safe pending retry, `move` as a write-ahead remote-then-local operation, and `push_tree` to reconcile a locally-written subtree. **The single most important fix of the day was a data-loss path that the spec described and the code had never implemented.** The spec's "Sync ordering" rule requires a local pending write to win over a same-cycle incoming delta for the same item, but `_apply_delta_item` never checked pending state at all — so a same-batch tombstone for an item whose `push_update` had failed (leaving `pending=True` after the remote delete) would unconditionally unlink the local file and drop the entry, destroying edits that had never been uploaded, while the pending-update loop's own comment claimed this was safely reconciled. Closing it took a coordinated set of changes rather than one guard: `_is_pending()` is re-verified under *each* commit lock rather than once up front (a single check-then-release leaves a race window for a concurrent push), the same guard extends to `sync()`'s separate out-of-scope-delta cleanup path which runs under a different lock scope and never calls `_apply_delta_item` at all, the cascade and folder-registration helpers gained `skip_pending`/`skip_if_pending` parameters so a folder tombstone still removes its non-pending descendants without being all-or-nothing in either direction, `delete()` now reports whether it actually made a Graph call (versus having been cascade-removed by an earlier ancestor delete in the same loop), and same-cycle stale-delta suppression is keyed to the **remote** etag actually observed via `get_item()` rather than the possibly-doubly-stale local one — never by id membership alone, and never on a bare `None == None`, which would otherwise treat any tombstone (they normally carry no eTag) as stale. One narrower gap was documented rather than closed: the move loop's pre-write etag is the local record, because `move_item()` takes no `If-Match` and there is no existing `get_item()` call to piggyback on, so fixing it would mean a network round-trip whose only purpose is that bookkeeping. Elsewhere the day's review rounds caught the kind of asymmetry that is easy to miss and expensive to hit: `push_tree`'s stale-deletion sweep checked only basename exclusions while the upload walk skipped dot-directories wholesale, so a tracked entry nested under a dot-directory could be *deleted remotely* by a sweep that would never have uploaded it; and `push_tree("")` computed its sweep prefix as `"/"`, which no real path starts with, silently turning the root-level sweep into a no-op. `push_update` reads the local file *before* recording its write-ahead marker (so an unreadable file can't strand an orphaned pending entry), both its confirm steps re-check that the local file still matches what was uploaded before clearing pending (so a second edit made mid-upload isn't lost), and the retry loop no longer deletes the local file on a remote 404 — a transient 404 reconverges, but a delete-then-re-upload does not, since Graph assigns a brand-new item id. `move` preserves a file's existing local basename (only the directory changes) so a locally-pushed real-named file isn't silently renamed to an id-stem, with four review-driven guards mirroring existing patterns in the file rather than inventing new ones. And `_prune_missing_after_full_resync` now sorts stale keys deepest-first, since processing a stale folder before its stale child would `rmdir()` a non-empty directory and swallow the `ENOTEMPTY`. The module still has **zero production wiring** — verified 08-18, no imports outside the package — which is also why no schema migration is needed for deployed caches: no real index files exist outside tests. Plan 3 (pipeline/watcher/webserver integration, plus the PP source directory) is the remaining work. **Stack:** Python (uv, FastAPI, Playwright, Claude API). Port 8765. 590 tests across 38 files (149 of them covering `graph/`).

#### siem-forwarder
Niagara 4 JACE module that forwards security-relevant BACnet MS/TP operations to a SIEM over RFC 5424 syslog/TLS, built around a non-interference design: a bounded drop-oldest queue drained by a below-normal-priority worker thread, and self-throttling with explicit gap events. **The design changed shape on 2026-08-11.** PNNL's answer to a July design-clarification email — capture *all* traffic on the RS-485 bus, not just points already monitored elsewhere — is more than the original ride-along point-COV pattern could ever deliver, since ride-along only ever saw Niagara-abstracted values for points some other component already had subscribed, never the on-wire operations that matter for security (Who-Is/Who-Has recon sweeps, priority-array WriteProperty seizures, `DeviceCommunicationControl`/`ReinitializeDevice`, a new MAC joining the token ring). So SDD v1.5 **retired ride-along outright** rather than keeping it as a second collector, and v1.6 **retired alarm forwarding too**: the SDD §13 passive MS/TP listener — a receive-only second serial port jumpered onto the live trunk, running a custom frame state machine and BACnet APDU decoder that is *not* layered on Tridium's driver — is now the module's sole collector, and RS-485 field-bus traffic is its entire scope. Audit/platform logs remain deferred to Niagara's own native remote syslog (4.10+). Non-interference is redefined along with it: no longer "add no polls" but electrical and receive-only invariants (never assert driver-enable, no double-termination on a mid-segment tap, stay inside the trunk's unit-load budget), plus an admission-control hook the current self-throttle doesn't have yet — it gates already-decoded events, so it cannot protect the capture/decode path, and line-rate decode on a busy 38.4k/76.8k trunk is the design's primary risk. Feasibility questions closed against the indexed Niagara 4.10/4.15 module cache: `javax.baja.serial.BISerialService` is reachable via the same `Sys.getService()` pattern the module already uses, port ownership is an exclusive lock with no supported way to tap the live driver's frames (so the two-port jumper is the only route, not merely the safer one), and the serial-port license caveat is now confirmed low-risk from declared-symbol evidence, pending a real JACE's License Manager. SDD is at **v1.8 (draft)** with test cases T13–T16 added for the listener; `MstpPassiveListener.java` does not exist yet and `RideAlongSubscriber.java` is marked obsolete for Phase 1 deletion. **08-12 was a documentation-only day, and it split the SDD into two documents.** `siemForwarder-SDD.docx` is now the customer-facing variant — Section 11 and Appendices A/B dropped entirely, Sections 12 and 13 renumbered to 11 and 12 throughout (headings, TOC, and every prose cross-reference), the Revision History section removed, and fields set to force Word to recalculate stale TOC page numbers on open. `siemForwarder-SDD-Internal.docx` keeps Section 11 with its findings in the confirmed/verified tense that actually matches the committed Java skeleton. That divergence is deliberate and worth knowing before editing either: the customer copy describes as "anticipated" a set of fixes the skeleton source already contains, a choice of how the document reads over strict consistency with the code, made after the pre-commit review flagged the mismatch twice. Test case T12 was also split, since its original pass criterion covered RS-485/MS-TP metrics that don't exist until the Phase 2 listener is built and a Phase 1 run could only have passed it trivially — T12 now covers the pre-listener metrics, and a new T17 re-runs non-interference with the listener in place. A `siemForwarder-PilotCostProposal-DRAFT.docx` (PNNL, $230/hr, dated 12 Aug 2026, 60-day validity) prices a single-site, single-trunk pilot in two phases — close the baseline module's remaining framework bind points and run the verification plan, then implement the listener — re-cited against the customer SDD's new numbering, with documentation hours doubled in both phases and T17 priced in, for a combined 272–448 hrs / $62,560–$103,040. **Stack:** Java (Niagara 4 module API, Gradle).
