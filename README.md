#### rfp-automation
Automated extraction, analysis, and proposal generation for DoD/MILCON cybersecurity RFPs. Parses specs and drawings, classifies cyber governance (UFGS 25 05 11 / 25 08 11), extracts scope, builds submittal matrices, and generates draft proposals. 2026 additions: email intake with PIID identity gate, bid follow-up tracking with Planner comment integration, amendment cyber review (local Ollama for CUI, cloud otherwise), redesigned dashboard with SSE live updates, per-project Ask-AI chat, a launchd-driven SENTRY self-improvement loop, and (August) a **missing-RFP-docs flag** — a pipeline-independent watch-loop sweep that surfaces MISC-type project folders whose `0.RFP/` holds no source documents, which `parser.discover_projects` had been filtering out silently. Surfaces in the dashboard attention inbox and the daily digest, behind `RFP_MISSING_DOCS_ENABLED`. None corrupts file *content*, and the deployment is single-writer-per-root anyway, but the self-healing claim needs one carve-out: the resurrect-on-delete race leaves a stale index entry that an *incremental* sync will not clear, because the tombstone that would remove it was already consumed and the delta token advanced past it — only a full resync prunes it. The others do self-heal on a later sync or resolve. Closing them properly needs a second, coarser whole-`sync()` lock, which is a real design addition tracked as follow-up rather than improvised here. **2026-08-18 delivered Plan 2 of 3 in a single day — sixteen commits — and resolved the credential question that had been gating the whole migration.** Owen chose **(a) reuse rfp-automation/SENTRY's existing certificate and app registration** rather than provisioning a separate one; that has no code impact on this plan (auth is Plan 1 code) but unblocks Plan 3 to proceed to live credentials. Plan 2 itself is the **nested-cache retrofit**, and its necessity is worth stating plainly: Plan 1's `Cache` stored every file flat under `cache_dir` with an id-derived stem, which is structurally incompatible with how the app already reads the vault — `dashboard.py` does `vault_root.iterdir()` and `sub.glob("*.docx")`, and the webserver mounts `StaticFiles(vault_root)`. The locked spec's promise that "everything downstream keeps doing ordinary `Path` I/O unchanged" simply could not hold on a flat store, which is why this was recorded as the known blocker on 08-17. So `CacheEntry.local_filename` changed meaning from a bare filename to a root-relative POSIX path, with paths derived by walking `parent_id` ancestry through the index and **healing unknown ancestors on demand** (fetching and registering parent folders from Graph), so derivation never depends on the order Graph happens to emit a delta batch. A per-root **naming policy** decides which files keep their real basename — the app-authored deterministic ones (`summary.md`, `email.*`, `*.docx`) that downstream globs actually look for — versus which get the collision-safe id-stem (everything externally named, where a hostile or colliding filename is a real risk). The same plan added the write-side primitives Plan 3 will call: `create_folder` (with 409-adopt), `ensure_remote_dir` to walk and create remote folder chains, `push_update` with `If-Match` and crash-safe pending retry, `move` as a write-ahead remote-then-local operation, and `push_tree` to reconcile a locally-written subtree. **The single most important fix of the day was a data-loss path that the spec described and the code had never implemented.** The spec's "Sync ordering" rule requires a local pending write to win over a same-cycle incoming delta for the same item, but `_apply_delta_item` never checked pending state at all — so a same-batch tombstone for an item whose `push_update` had failed (leaving `pending=True` after the remote delete) would unconditionally unlink the local file and drop the entry, destroying edits that had never been uploaded, while the pending-update loop's own comment claimed this was safely reconciled. Closing it took a coordinated set of changes rather than one guard: `_is_pending()` is re-verified under *each* commit lock rather than once up front (a single check-then-release leaves a race window for a concurrent push), the same guard extends to `sync()`'s separate out-of-scope-delta cleanup path which runs under a different lock scope and never calls `_apply_delta_item` at all, the cascade and folder-registration helpers gained `skip_pending`/`skip_if_pending` parameters so a folder tombstone still removes its non-pending descendants without being all-or-nothing in either direction, `delete()` now reports whether it actually made a Graph call (versus having been cascade-removed by an earlier ancestor delete in the same loop), and same-cycle stale-delta suppression is keyed to the **remote** etag actually observed via `get_item()` rather than the possibly-doubly-stale local one — never by id membership alone, and never on a bare `None == None`, which would otherwise treat any tombstone (they normally carry no eTag) as stale. One narrower gap was documented rather than closed: the move loop's pre-write etag is the local record, because `move_item()` takes no `If-Match` and there is no existing `get_item()` call to piggyback on, so fixing it would mean a network round-trip whose only purpose is that bookkeeping. Elsewhere the day's review rounds caught the kind of asymmetry that is easy to miss and expensive to hit: `push_tree`'s stale-deletion sweep checked only basename exclusions while the upload walk skipped dot-directories wholesale, so a tracked entry nested under a dot-directory could be *deleted remotely* by a sweep that would never have uploaded it; and `push_tree("")` computed its sweep prefix as `"/"`, which no real path starts with, silently turning the root-level sweep into a no-op. `push_update` reads the local file *before* recording its write-ahead marker (so an unreadable file can't strand an orphaned pending entry), both its confirm steps re-check that the local file still matches what was uploaded before clearing pending (so a second edit made mid-upload isn't lost), and the retry loop no longer deletes the local file on a remote 404 — a transient 404 reconverges, but a delete-then-re-upload does not, since Graph assigns a brand-new item id. `move` preserves a file's existing local basename (only the directory changes) so a locally-pushed real-named file isn't silently renamed to an id-stem, with four review-driven guards mirroring existing patterns in the file rather than inventing new ones. And `_prune_missing_after_full_resync` now sorts stale keys deepest-first, since processing a stale folder before its stale child would `rmdir()` a non-empty directory and swallow the `ENOTEMPTY`. The module still has **zero production wiring** — verified 08-18, no imports outside the package — which is also why no schema migration is needed for deployed caches: no real index files exist outside tests. Plan 3 (pipeline/watcher/webserver integration, plus the PP source directory) is the remaining work. **Stack:** Python (uv, FastAPI, Playwright, Claude API). Port 8765. 590 tests across 38 files (149 of them covering `graph/`).

The root cause got a direct fix too — `SCRIBE_ASR_LANGUAGE` pins ASR to English so Whisper stops auto-detecting a quiet opening as Japanese. Precision over recall throughout: a general "short non-ASCII lead-in" rule was tried and rejected in review. 08-13 added no code, but landed an approved design (pending an implementation plan) for **auto-detecting screen sharing** so a forgotten 🖥️ Capture-screen click stops costing the shared content: a browser extension whose content scripts watch Google Meet and Teams-in-browser presenting state and relay a prompt to the active recording tab, reusing the existing `getDisplayMedia` flow with no backend change. The first pass — native per-OS watchers polling window state — was rejected in review for reasons verified against the code: it would need a background process installed on *every* platform, the macOS agent records with no browser tab open at all, meeting-scoped SSE fans out to every logged-in device so a prompt could surface where `getDisplayMedia()` would capture the wrong screen, and full-motion capture can't be restarted within a meeting. **08-14 built it — 28 commits in one day, and it is the largest single feature scribe has landed since the repo split.** The `extension/` directory now holds a real MV3 Chrome/Edge extension: a background service worker, Meet and Teams content scripts over a shared pure `presence-detect.js` text-pattern detector, a pure `share-state.js` transition module, a `content-scribe-bridge.js` relay into the web app, and an options page for the one-time Scribe-origin permission grant (`optional_host_permissions`, so Chrome grants exactly one address and nothing broader). It stays entirely client-side — no new backend routes, no server-side state — and `startScreenCapture()` was extracted out of the manual button so more than one thing can trigger it, with a new public `canStartScreenCapture()` on `MeetingRecorder` and an auto-detect toast in the recording view. Scope is honest in the user guide: Zoom and the Teams desktop app are invisible to a browser extension and still need the manual button, and if the extension isn't installed or a Meet/Teams UI change breaks detection, **Capture screen** always still works on its own. Roughly half those commits are review-driven fixes, and they are mostly *concurrency* fixes — the interesting ones being a prompt-dedup heuristic replaced with a provably-correct `allowPrompt` flag (the leaving transitions can never make a prompt newly true, so they can only ever clear), token-scoping extended to the outbound `prompt`/`clear` relays after inbound-only scoping left `chrome.tabs.sendMessage` latency able to deliver recording A's message to recording B in the same tab, a permission rollback rebased on an actual pre-existing-grant check instead of a pattern-comparison proxy that could revoke a working grant, and `reconcilePresence()` falling back to `chrome.scripting.executeScript()` for tabs opened *before* the extension was installed, since declarative content-script registration only applies to future page loads.
